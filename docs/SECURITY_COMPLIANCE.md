# Контроль соответствия AlMaBi

Документ предназначен для **службы безопасности (СБ)**, владельца системы,
ответственного за ПДн и администратора эксплуатации. Описывает состав данных,
реализованные технические меры, статус устранения замечений аудита и
организационные решения, которые СБ должна подтвердить до production rollout.

Связанные материалы:

- эксплуатация, backup и rollback — `docs/SECURITY_OPERATIONS.md`;
- переменные окружения — `.env.example`;
- автоматическая приёмка — `scripts/security_acceptance.ps1`.

## 1. Назначение системы и контур

AlMaBi — внутреннее BI-приложение для построения P&L по Excel-выгрузкам 1С.
Предполагаемый контур эксплуатации:

- доступ только из утверждённых LAN/VPN-подсетей;
- HTTPS через reverse proxy (`nginx` + TLS);
- вход: своя страница `/login` → Keycloak 26.5 → Active Directory → мультифактор;
- данные хранятся на площадке заказчика (Docker volumes).

Production-стек: `docker-compose.prod.yml`. Dev-режим (`docker-compose.yml`,
`AUTH_ENABLED=false`) **не является эталоном безопасности** и используется
только для локальной разработки.

## 2. Инвентаризация данных

| Категория | Содержимое | Расположение | Примечание для СБ |
|---|---|---|---|
| Исходные выгрузки 1С | финансовые операции, договоры, проекты, контрагенты, возможные ПДн в свободных полях | volume `uploads`, каталоги `{user_id}/` | основной объект защиты |
| Производные BI-данные | P&L, налоговые разрезы, drill-down, сверки | вычисляются в памяти; не выгружаются в отдельную БД | не сохраняются между запросами |
| Учётные данные | логин, роль, срок сессии и простой | Postgres, контейнер `db`, порт 5432 только внутри Docker | пароль, срок пароля и второй фактор — в Keycloak 26.5; локальный хеш только без Keycloak |
| Технические журналы | request ID, маршрут, статус, длительность | volume `logs` | без содержимого загруженных файлов |
| Детальный расчётный audit | пути к файлам, строки сверки | `logs/` (если включён) | **выключен по умолчанию** (`AUDIT_DETAIL_ENABLED=false`) |

Владелец процесса до production-ввода обязан подтвердить:

- содержит ли обработка ПДн и какие категории субъектов затронуты;
- цели и правовые основания обработки;
- сроки хранения uploads/logs/backup;
- необходимость уведомления Роскомнадзора и локализации баз.

## 3. Модель доступа (RBAC)

| Роль | Просмотр BI | Загрузка Excel | Управление пользователями | Детальный audit | Swagger `/api/docs` |
|---|---:|---:|---:|---:|---:|
| `viewer` | да | нет | нет | нет | нет |
| `uploader` | да | да | нет | нет | нет |
| `admin` | да | да | да | только при явном включении | да |

Дополнительные ограничения:

- неаутентифицированный доступ закрыт для всех маршрутов, кроме `/login`,
  `/login/keycloak`, `/login/callback`, `/health`, `/ready` и статики;
- state-changing запросы (POST/PUT/PATCH/DELETE) требуют CSRF-токен;
- загрузки изолированы по пользователю (`uploads/{user_id}/`);
- `/health` и `/ready` публикуются только во внутренний контур reverse proxy;
- перебор пароля на входе закрывает Keycloak; локальной формы пароля в AlMaBi нет.

## 4. Реализованные технические меры

### 4.1. Аутентификация и сессии

- production: кнопка «Войти» на своей странице ведёт в Keycloak 26.5; иные версии не используются;
- в Keycloak, не в AlMaBi: учётные записи Active Directory, парольная политика, срок пароля, мультифактор и защита от перебора входа;
- после успешного входа Keycloak отдаёт роль, AlMaBi открывает свою сессию и записывает пользователя в Postgres;
- локальной формы логина и пароля нет;
- серверные сессии с отзывом (`create_session` / `revoke_session`);
- signed cookie только как указатель на серверную сессию;
- `SESSION_HTTPS_ONLY=true` и `SESSION_MAX_AGE_SECONDS` (по умолчанию 8 ч);
- при `AUTH_ENABLED=true` и `DEBUG=false` приложение не стартует со слабым
  `SESSION_SECRET` (< 32 символов) или без HTTPS-only cookie.

### 4.2. Защита веб-приложения

- CSP с `nonce` для inline-скриптов, без внешних script/style/font CDN;
- заголовки: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
  `Permissions-Policy`, HSTS (через nginx и middleware);
- `TrustedHostMiddleware` по `ALLOWED_HOSTS`;
- HTML-экранирование пользовательских данных в шаблонах и JS;
- CSRF для форм и upload API.

### 4.3. Файлы и загрузки

- валидация имён файлов и запрет path traversal (`almabi_file_security.py`);
- лимит тела запроса и квота на пользователя (`MAX_UPLOAD_BYTES`,
  `UPLOAD_QUOTA_BYTES`);
- проверка контейнера XLSX (zip bomb, шифрование);
- таймаут обработки запроса.

### 4.4. Сеть и инфраструктура

- `nginx`: TLS 1.2/1.3, HSTS, rate limit (120 req/min), limit_conn (20);
- фильтрация по RFC1918/loopback в `ops/nginx.conf` (требует настройки под
  фактические LAN/VPN CIDR);
- `web` не публикует порт на хост, доступен только из internal network;
- контейнеры без root (`web`: UID 10001, `nginx`: UID 101);
- read-only root FS, `cap_drop: ALL`, `no-new-privileges`, лимиты CPU/RAM/PID.

### 4.5. Зависимости и сборка

- Python-зависимости зафиксированы в `requirements.lock` с хешами;
- `pip-audit` и `npm audit --audit-level=high` входят в приёмку;
- `.dockerignore` исключает `.env`, ключи TLS, dev-скрипты из build context;
- Chart.js и шрифты Inter — локально (`static/dist`), без CDN.

### 4.6. Журналирование и retention

- JSON-логи запросов без содержимого файлов;
- детальный расчётный audit скрыт по умолчанию;
- политика хранения: `UPLOAD_RETENTION_DAYS` (90), `LOG_RETENTION_DAYS` (30);
- очистка выполняется процессом `web` не чаще чем раз в 10 дней.

## 6. Обязательные организационные решения (подтверждает СБ)

До допуска в production СБ совместно с владельцем системы фиксирует:

1. **Владельцы и роли**: системный владелец, администратор приложения,
   ответственный за ПДн, контакт при инциденте (24×7 или в рабочие часы).
2. **Статус ИСПДн**: является ли обработка персональных данными; при «да» —
   уровень защищённости по ПП РФ №1119 и набор мер по приказу ФСТЭК №21.
3. **Правовые основания**: политика обработки, согласия (если применимо),
   необходимость уведомления Роскомнадзора (152-ФЗ).
4. **Локализация**: подтверждение, что первичные базы и backup остаются на
   территории РФ (если применимо к организации).
5. **Матрица доступа**: перечень пользователей и ролей; пересмотр не реже
   1 раза в квартал.
6. **Retention и удаление**: uploads 90 дней, логи 30 дней; процесс `web`
   очищает их не чаще раза в 10 дней, журнал — `logs/retention.jsonl`.
7. **Сеть**: фактические LAN/VPN CIDR в `ops/nginx.conf`; запрет публикации
   порта 8000; правила Windows Firewall / корпоративного балансировщика.
8. **TLS**: сертификат с корректным SAN; для внутреннего CA — доверие на
   рабочих станциях; план ротации до истечения срока.
9. **КИИ / ГИС / 187-ФЗ**: применимость определяется отдельным решением
   юриста; технические меры AlMaBi не заменяют организационный контур КИИ.
10. **Коммерческая тайна (98-ФЗ)**: при необходимости — режим доступа к
    выгрузкам, NDA, запрет копирования вне контура.

## 8. Остаточные риски (принять или доработать)

| Риск | Уровень | Компенсирующие меры | Решение СБ |
|---|---|---|---|
| Docker Desktop на Windows — не HA | средний | выделенный Linux-host для production | ☐ принять ☐ доработать |
| Изменяемые tags base images | низкий | фиксация digest после scan | ☐ принять ☐ доработать |
| BI-расхождения PQ-only строк (не security) | низкий | документировано в тестах; не влияет на ACL | ☐ принять |
| Отсутствие WAF | низкий | LAN-only + rate limit + auth | ☐ принять ☐ доработать |

## 9. Реагирование на инцидент

1. Немедленно ограничить контур (остановить nginx / закрыть firewall),
   сохранить логи, отозвать сессии (`revoke_user_sessions` / смена
   `SESSION_SECRET` с перезапуском).
2. **Не позднее 24 часов**: первичная квалификация, владелец, масштаб,
   категории данных, меры локализации, решение об уведомлении РКН/ФСТЭК
   (при наличии ПДн / КИИ).
3. **Не позднее 72 часов**: причина, последствия, затронутые субъекты,
   корректирующие меры (152-ФЗ, изменения с 01.07.2025 — штрафы по 420-ФЗ
   при утечках).
4. Перед восстановлением: проверка backup, SHA-256 архивов, чистота image.
5. После инцидента: обновление модели угроз, чек-листа СБ, regression-тестов.

Юридические сроки и адресаты уведомлений **обязаны** быть подтверждены
ответственным юристом для конкретного состава данных и статуса организации.
AlMaBi не отправляет уведомления в госорганы автоматически.

## 11. Решения и что осталось

Зафиксировано:

- вход всех пользователей: своя страница → Keycloak 26.5; иные версии не используются. Active Directory и мультифактор подключает ИБ позже, в AlMaBi их нет;
- группы в токене Keycloak: `AlMaBi-Admins` — два именных администратора; `AlMaBi-Uploaders` — сотрудники с загрузкой Excel; `AlMaBi-Viewers` и все остальные — только просмотр. Человека добавляют в группу, AlMaBi учётку паролем не создаёт;
- принцип «четырёх глаз» закрывается двумя людьми в `AlMaBi-Admins`, отдельное подтверждение в системе не делается;
- SIEM подключат после ввода. Назначение: `srv-s.alabuga.ru` (`10.50.53.121`), TCP/1514 и TCP/1515. Название системы не фиксируется. Приложение само журналы не отправляет; для будущей отправки остаётся открытый JSON в консоли контейнера;
- файлы выгрузок и журналов шифруются ключом из `ops/secrets/data_key`. Без этого файла production не стартует;

Позже:

- автоматическая проверка загружаемых файлов на ПДн и конфиденциальные данные.
- подключение Active Directory и мультифактора в Keycloak 26.5 делает ИБ.
