# 07. Документация для проверки информационной безопасности

## 7.1. Краткое описание объекта защиты

Веб-приложение для построения управленческого P&L по Excel-выгрузкам 1С. Развёртывается в Docker. Доступ предполагается во **внутренней сети / VPN**. Содержит финансовые/управленческие данные из загружаемых файлов (выручка, себестоимость, договоры, контрагенты, налоговые режимы).

## 7.2. Активы

| Актив | Описание | Критичность |
|-------|----------|-------------|
| Excel-выгрузки 1С | `uploads/almabi/` | Высокая |
| Cookie-сессии (привязка файлов) | `SESSION_SECRET` | Высокая |
| Журналы / audit | `logs/`, `logs/almabi_test/` | Средняя |
| Исходный код / образ | репозиторий, Docker image | Средняя |
| Доступность сервиса | порт 18001 / reverse proxy | Средняя |
| OpenAPI UI | `/api/docs` | Средняя (разведка API) |

## 7.3. Модель доступа

| Субъект | Аутентификация | Авторизация |
|---------|----------------|-------------|
| Пользователь UI/API | **Нет** | Все функции доступны любому, кто достучался до порта |
| Мониторинг | Нет | `/health`, `/ready` |
| Администратор ОС | SSH / локальный доступ | Файлы, Docker, `.env` |

**Важно для аудита:** на момент комплекта **нет Basic Auth, SSO и RBAC**. Защита опирается только на сетевой периметр. Это **критичное отличие** от hardened ОПиОП BI v1.1.

## 7.5. Анализ угроз (упрощённый)

| ID | Угроза | Вектор | Реализованная защита | Остаточный риск |
|----|--------|--------|----------------------|-----------------|
| T01 | Несанкционированный доступ к P&L | Открытый порт без auth | Только сеть | **Высокий** без VPN/firewall |
| T02 | Перехват данных / cookie | HTTP без TLS | — | **Высокий без HTTPS** |
| T03 | DoS через большой upload | POST multipart | Тип .xlsx | **Высокий** (нет size/rate limit) |
| T04 | Разведка API | Открытый Swagger | — | Средний |
| T05 | Path traversal в имени файла | upload filename | `Path.name` + UUID | Низкий |
| T06 | XSS через данные Excel | имена в шаблонах | Jinja autoescape | Низкий/средний |
| T07 | Утечка содержимого uploads | доступ к FS / другой сессии при слабом секрете | UUID имена | Средний при слабом `SESSION_SECRET` |
| T08 | Компрометация `.env` | доступ к серверу | Права ОС | Зависит от hardening ОС |
| T09 | Неконтролируемый рост диска | частые upload | Нет автоочистки | Средний |
| T10 | Контейнер от root | RCE в приложении → root | — | Средний/высокий |
| T11 | Отсутствие RBAC | любой visitor = полный доступ | — | Высокий в multi-user |

## 7.6. Остаточные риски и рекомендации

### Обязательно до вывода в эксплуатацию (если доступ шире localhost)

1. **Ограничить сеть** — firewall / VPN; не публиковать `:18001` в интернет.
2. **TLS (HTTPS)** через nginx/traefik.
3. **Ввести аутентификацию** (Basic Auth / SSO) по аналогии с ОПиОП BI — иначе любой в сети видит финансы.
4. Сменить **`SESSION_SECRET`** на длинный случайный (≥32).
5. `DEBUG=false` в production compose; отключить OpenAPI в prod.
6. Регламент **бэкапа** `uploads/`, `.env`.

### Рекомендуется в следующих итерациях

1. `MAX_UPLOAD_BYTES` + rate limit upload.
2. Security headers (X-Frame-Options, nosniff, Referrer-Policy, CSP).
3. Non-root `USER` в Dockerfile.
4. Вынести pytest в `requirements-dev.txt`.
5. Cookie `Secure` / `https_only` при HTTPS.
6. RBAC (read-only vs upload).
7. Автоочистка старых uploads.
8. Централизованный сбор логов / алерты.
9. CI security-сканы зависимостей.

## 7.7. Обработка персональных данных

Типовой сценарий — **управленческая отчётность / договоры / контрагенты**, не целевая обработка ПДн физлиц.  
Если в выгрузках появляются ФИО сотрудников, табельные номера и т.п. — владелец обязан:

- классифицировать данные;
- применить 152-ФЗ / внутренние политики;
- ограничить доступ к порту и (после внедрения) к учётным записям;
- учесть сроки хранения файлов в `uploads/`.

**Вывод для аудита:** ПДн не заложены в модель явно; риск определяется содержимым выгрузок 1С.

## 7.8. Соответствие ожиданиям «internal BI»

| Критерий | Оценка |
|----------|--------|
| Готовность к internal prod за VPN + HTTPS **без доработок auth** | **Нет** — отсутствует аутентификация |
| Готовность после внедрения auth + hardening (как ОПиОП) + VPN + HTTPS | **Да**, при выполнении п. 7.6 |
| Готовность к публичному интернету | **Нет** |
| Наличие документации для ИБ | Настоящий комплект |
