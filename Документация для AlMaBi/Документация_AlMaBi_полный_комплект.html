01. Описание проекта

1.1. Назначение

Al Ma BI (AlMaBi) — веб-приложение для построения управленческого P&L (БДР) по выгрузкам 1С в формате Excel.

Система:

  • загружает и проверяет обязательный набор выгрузок: бух.регистр, реализация, себестоимость;
  • опционально принимает файл план/прогноз;
  • строит Power Query–совместимые таблицы и факты P&L (БУ / НУ / план / прогноз);
  • показывает сводный дашборд «Тест BI» с фильтрами, drill-down, карточками контрагентов и графиками;
  • предоставляет отдельные отчёты по KPI (выручка, себестоимость, прочие доходы/расходы, налоги, чистая прибыль и др.);
  • предоставляет health/readiness для мониторинга.

1.2. Границы системы

Входит в scope

  • Веб-UI дашборда, графиков, «Тест Excel» и KPI-отчётов.
  • API загрузки Excel-выгрузок и получения JSON payload для отчётов.
  • Парсинг и join выгрузок 1С с логикой, совместимой с Power Query.
  • Локальная сборка frontend (Vite + Tailwind).
  • Docker-развёртывание.

Не входит в scope

  • Аутентификация / SSO / LDAP / AD / Basic Auth (на момент комплекта нет).
  • Разграничение ролей (RBAC).
  • Аналитическое хранилище (DWH) и реляционная БД фактов — данные не нормализуются в витрину СУБД.
  • Реестр версий файлов в SQLite (в отличие от ОПиОП BI): выбор файлов хранится в cookie-сессии браузера.
  • Высокая доступность и горизонтальное масштабирование.
  • Встроенный TLS — ожидается reverse proxy (nginx/traefik) и ограничение сети.

03. Архитектура хранилища

3.1. Общий принцип

Система не хранит аналитические факты в реляционной БД.

Что Где
Содержимое Excel-выгрузок Файловая система (uploads/almabi/)
Привязка файлов к пользователю Signed cookie-сессия браузера
Кеш / runtime runtime/ (служебные каталоги)
Логи приложения logs/app.log (и связанные)
Audit pipeline logs/almabi_test/audit-*.json

Это упрощает развёртывание (один контейнер), но:

  • нет общей истории версий между браузерами;
  • масштабирование нескольких реплик требует общей FS или внешней сессии;
  • бэкап критичен для uploads/ и .env.

3.2. СУБД

Отсутствует. Метаданные файлов не ведутся в SQLite (в отличие от ОПиОП BI).

3.3. Файловое хранилище

AlMaBi/
├── uploads/
│   └── almabi/
│       ├── buh-{uuid}.xlsx
│       ├── realization-{uuid}.xlsx
│       ├── cost-{uuid}.xlsx
│       └── … план/прогноз (если загружен)
├── runtime/                 # служебный каталог (готовность /ready)
└── logs/
    ├── app.log
    └── almabi_test/
        ├── audit-latest.json
        └── audit-{id}.json

Docker volumes (compose)

Хост Контейнер
./uploads /app/uploads
./runtime /app/runtime
./logs /app/logs

Весь репозиторий в /app не монтируется, чтобы не затирать собранные static/dist.

3.4. Сессионная модель

Ключи сессии:

Ключ Содержимое
almabi_upload_set { buh\|realization\|cost: { original, stored } }
almabi_plan_forecast { original, stored } (опционально)

Путь на диске: UPLOADS_DIR/almabi/{stored}.

3.5. Жизненный цикл файла

  1. Upload: сохранение под UUID-именем в uploads/almabi/.
  2. Валидация типа выгрузки (validate_almabi_export).
  3. Запись метаданных в cookie-сессию.
  4. При следующем запросе дашборда файлы читаются с диска по session paths.
  5. Удаление старых файлов из UI не реализовано (рост uploads/ — административно).

3.6. Диаграмма (логическая)

Session cookie
  almabi_upload_set.buh.stored ──────────► uploads/almabi/buh-{uuid}.xlsx
  almabi_upload_set.realization.stored ──► uploads/almabi/realization-{uuid}.xlsx
  almabi_upload_set.cost.stored ─────────► uploads/almabi/cost-{uuid}.xlsx
  almabi_plan_forecast.stored ───────────► uploads/almabi/…xlsx

Pipeline (in-memory)
  BuhRow / RealizationRow / CostRow → Fact → dashboard / reports

Аналитическая модель (факты P&L) не материализуется в БД — строится на лету.

3.7. Рекомендации по сопровождению

  • Бэкапить uploads/, logs/ (по политике), .env.
  • Периодически чистить старые uploads/almabi/*.xlsx.
  • Не коммитить uploads/, logs/, runtime/, .env в git.
  • При нескольких инстансах обеспечить общее хранилище uploads и sticky sessions / общий secret.

05. Модель данных Excel и P&L

5.1. Входные выгрузки

Тип Ключ Обязательность Маркеры заголовков (упрощённо)
Бух.регистр buh Да документ + сумма + счет дт
Реализация realization Да выручка + (номенклатура / заказ клиента / группа проектов / направление)
Себестоимость cost Да продукция / документ отгрузки + колонки себестоимости
План / прогноз session almabi_plan_forecast Нет сумма + месяц + план/прогноз

Формат: только .xlsx. Тип определяется по заголовкам (первые ~40 строк) и эвристикам имени файла.

5.2. Бух.регистр → BuhRow

Основные поля: документ, счет Дт/Кт, сумма БУ, суммы НУ Дт/Кт, месяц, вид налогообложения, статья расходов, договор, проект, номенклатура Кт, контрагент.

Особенности PQ:

  • skip ≈ 8 строк заголовка, последняя служебная строка отбрасывается;
  • вид налогообложения извлекается из субконто (приоритет PQ);
  • статья прочих доходов/расходов — из субконто стороны 91.01 / 91.02.

5.3. Реализация → RealizationRow

Поля: документ, номенклатура, проект, группа проектов, направление, выручка, месяц, договор.

5.4. Себестоимость → CostRow

Поля: документ, номенклатура (продукция), счет, статья калькуляции, количество продаж, сумма, месяц, раздел себестоимости, аналитика, договор.

Разделы (PQ): при счёте ≠ 20 — «Прочие производственные расходы»; для счёта 20 — материалы / ФОТ / аренда / амортизация / ОПЗ и др. по статье калькуляции.

5.5. План / прогноз

Обязательные нормализованные заголовки: сумма, месяц, план/прогноз.
Опциональные измерения: направление, группа, проект, вид налогообложения, раздел, вид себестоимости.

Без файла план/прогноз сценарии могут аппроксимироваться коэффициентами от факта (см. almabi_mock_data.SCENARIOS).

5.6. Поток построения фактов («Тест BI»)

parse exports
  → индексы doc_tax / doc_contract / doc_contractor
  → project_index + realization_lookup + cost PQ lookup
  → classify_buh_section → signed amounts → Fact
  → (прочие) storno / NU split при расхождении БУ и НУ
  → dashboard / reports

Join (кратко)

  1. Налог документа (doc_tax): льготный приоритетнее; выручка 90.01.3 может перезаписать.
  2. Себестоимость: ключ (document_match_key, nomenclature).
  3. Реализация: договор+номенклатура → договор → документ+номенклатура → документ.
  4. Аналитика: coalesce cost/realization → при конфликте realization → fallback project_index.
  5. Fallback: если из буха нет выручки/себестоимости — дополнение из файлов реализации/себестоимости.

Знаки сумм

  • Выручка / прочие доходы: положительные.
  • Себестоимость / коммерческие / управленческие / прочие расходы: отрицательные (как в PQ «Свод_нов»).

5.7. Налоговые корзины (tax_bucket)

Условие Корзина
«общие условия» / пусто Нельготные проекты
льгот, пониженн, ставка 0, эконом. зона, … Льготные проекты
Иное Нельготные проекты

UI-фильтр: Все виды / Льготные / Нельготные (+ направление, группа, проект, договор, контрагент, квартал, месяц).

5.8. Формулы свода P&L

Сценарии: Факт БУ, Факт НУ, План, Прогноз.

Операционная прибыль
  = Выручка + Себестоимость + Коммерческие + Управленческие

Прибыль/убыток до налогообложения
  = Операционная + Прочие доходы + Прочие расходы

Налоги (расчёт)
  = −base × rate
  rate = 0.02 если вид содержит «льгот», иначе 0.25
  (база — по НУ компонентам PBT в разрезе месяц × вид НО)

Чистая прибыль
  = PBT + Налоги

Замечание: для отображения выручки сценарий «Факт БУ» может брать НУ-суммы (always_nu).

5.9. Иерархия drill-down

Выручка / Себестоимость:
  KPI → направление → группа проектов → проект → договор

Льготные / прочие статьи:
  KPI → tax_bucket → [статья] → договор

5.10. Прочие доходы/расходы: storno и split БУ/НУ

  • Документы, где |БУ| и |НУ| > 0.01 и различаются → nu_mismatch_docs.
  • Storno-группы по (document, section, round(|amount|, 2)).
  • Общая налоговая сторно-строка может наследовать льготный НО от зеркальной проводки.
  • Если корзина налога БУ ≠ НУ → две Fact-строки (БУ-only и НУ-only).

07. Документация для проверки информационной безопасности

7.1. Краткое описание объекта защиты

Веб-приложение для построения управленческого P&L по Excel-выгрузкам 1С. Развёртывается в Docker. Доступ предполагается во внутренней сети / VPN. Содержит финансовые/управленческие данные из загружаемых файлов (выручка, себестоимость, договоры, контрагенты, налоговые режимы).

7.2. Активы

Актив Описание Критичность
Excel-выгрузки 1С uploads/almabi/ Высокая
Cookie-сессии (привязка файлов) SESSION_SECRET Высокая
Журналы / audit logs/, logs/almabi_test/ Средняя
Исходный код / образ репозиторий, Docker image Средняя
Доступность сервиса порт 18001 / reverse proxy Средняя
OpenAPI UI /api/docs Средняя (разведка API)

7.3. Модель доступа

Субъект Аутентификация Авторизация
Пользователь UI/API Нет Все функции доступны любому, кто достучался до порта
Мониторинг Нет /health, /ready
Администратор ОС SSH / локальный доступ Файлы, Docker, .env

Важно для аудита: на момент комплекта нет Basic Auth, SSO и RBAC. Защита опирается только на сетевой периметр. Это критичное отличие от hardened ОПиОП BI v1.1.

7.6. Остаточные риски и рекомендации

Обязательно до вывода в эксплуатацию (если доступ шире localhost)

  1. Ограничить сеть — firewall / VPN; не публиковать :18001 в интернет.
  2. TLS (HTTPS) через nginx/traefik.
  3. Ввести аутентификацию (Basic Auth / SSO) по аналогии с ОПиОП BI — иначе любой в сети видит финансы.
  4. Сменить SESSION_SECRET на длинный случайный (≥32).
  5. DEBUG=false в production compose; отключить OpenAPI в prod.
  6. Регламент бэкапа uploads/, .env.

Рекомендуется в следующих итерациях

  1. MAX_UPLOAD_BYTES + rate limit upload.
  2. Security headers (X-Frame-Options, nosniff, Referrer-Policy, CSP).
  3. Non-root USER в Dockerfile.
  4. Вынести pytest в requirements-dev.txt.
  5. Cookie Secure / https_only при HTTPS.
  6. RBAC (read-only vs upload).
  7. Автоочистка старых uploads.
  8. Централизованный сбор логов / алерты.
  9. CI security-сканы зависимостей.

7.7. Обработка персональных данных

Типовой сценарий — управленческая отчётность / договоры / контрагенты, не целевая обработка ПДн физлиц.
Если в выгрузках появляются ФИО сотрудников, табельные номера и т.п. — владелец обязан:

  • классифицировать данные;
  • применить 152-ФЗ / внутренние политики;
  • ограничить доступ к порту и (после внедрения) к учётным записям;
  • учесть сроки хранения файлов в uploads/.

Вывод для аудита: ПДн не заложены в модель явно; риск определяется содержимым выгрузок 1С.

7.8. Соответствие ожиданиям «internal BI»

Критерий Оценка
Готовность к internal prod за VPN + HTTPS без доработок auth Нет — отсутствует аутентификация
Готовность после внедрения auth + hardening (как ОПиОП) + VPN + HTTPS Да, при выполнении п. 7.6
Готовность к публичному интернету Нет
Наличие документации для ИБ Настоящий комплект
