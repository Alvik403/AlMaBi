# 03. Архитектура хранилища

## 3.1. Общий принцип

Система **не хранит аналитические факты в реляционной БД**.

| Что | Где |
|-----|-----|
| Содержимое Excel-выгрузок | Файловая система (`uploads/almabi/`) |
| Привязка файлов к пользователю | Signed cookie-сессия браузера |
| Кеш / runtime | `runtime/` (служебные каталоги) |
| Логи приложения | `logs/app.log` (и связанные) |
| Audit pipeline | `logs/almabi_test/audit-*.json` |

Это упрощает развёртывание (один контейнер), но:

- нет общей истории версий между браузерами;
- масштабирование нескольких реплик требует общей FS или внешней сессии;
- бэкап критичен для `uploads/` и `.env`.

## 3.2. СУБД

**Отсутствует.** Метаданные файлов не ведутся в SQLite (в отличие от ОПиОП BI).

## 3.3. Файловое хранилище

```
AlMaBi/
├── uploads/
│   └── almabi/
│       ├── buh-{uuid}.xlsx
│       ├── realization-{uuid}.xlsx
│       ├── cost-{uuid}.xlsx
│       └── … план/прогноз (если загружен)
├── runtime/                 # служебный каталог (готовность /ready)
└── logs/
    ├── app.log
    └── almabi_test/
        ├── audit-latest.json
        └── audit-{id}.json
```

### Docker volumes (compose)

| Хост | Контейнер |
|------|-----------|
| `./uploads` | `/app/uploads` |
| `./runtime` | `/app/runtime` |
| `./logs` | `/app/logs` |

Весь репозиторий в `/app` **не монтируется**, чтобы не затирать собранные `static/dist`.

## 3.4. Сессионная модель

Ключи сессии:

| Ключ | Содержимое |
|------|------------|
| `almabi_upload_set` | `{ buh\|realization\|cost: { original, stored } }` |
| `almabi_plan_forecast` | `{ original, stored }` (опционально) |

Путь на диске: `UPLOADS_DIR/almabi/{stored}`.

## 3.5. Жизненный цикл файла

1. Upload: сохранение под UUID-именем в `uploads/almabi/`.
2. Валидация типа выгрузки (`validate_almabi_export`).
3. Запись метаданных в cookie-сессию.
4. При следующем запросе дашборда файлы читаются с диска по session paths.
5. Удаление старых файлов из UI **не реализовано** (рост `uploads/` — административно).

## 3.6. Диаграмма (логическая)

```
Session cookie
  almabi_upload_set.buh.stored ──────────► uploads/almabi/buh-{uuid}.xlsx
  almabi_upload_set.realization.stored ──► uploads/almabi/realization-{uuid}.xlsx
  almabi_upload_set.cost.stored ─────────► uploads/almabi/cost-{uuid}.xlsx
  almabi_plan_forecast.stored ───────────► uploads/almabi/…xlsx

Pipeline (in-memory)
  BuhRow / RealizationRow / CostRow → Fact → dashboard / reports
```

Аналитическая модель (факты P&L) **не материализуется в БД** — строится на лету.

## 3.7. Рекомендации по сопровождению

- Бэкапить `uploads/`, `logs/` (по политике), `.env`.
- Периодически чистить старые `uploads/almabi/*.xlsx`.
- Не коммитить `uploads/`, `logs/`, `runtime/`, `.env` в git.
- При нескольких инстансах обеспечить общее хранилище uploads и sticky sessions / общий secret.
